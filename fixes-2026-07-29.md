## F1 — Flat spot is not flat *(done)*

**Changed:** `injection.py` — `_fine_wedge`, `wedge_peak_amplitude`,
`model_wedge_response`, `inject_dhi_anomaly`, `inject_dhi_anomaly_3d`.
`flat_spot_offset_ms` (an offset below the dipping top) replaced with
`contact_time_ms` (an absolute two-way time). In `inject_dhi_anomaly_3d`,
`contact_time_ms` is now derived once per injection from the footprint's own
structural relief (`crest_time_ms + contact_frac * relief_ms`, default
`contact_frac=0.5`), computed in a pre-pass before the per-voxel loop. Raises
if the footprint's relief is below `500/freq_hz` ms (half a Ricker cycle) —
too small for the contact to be a separable event from the top reflector.
The flat-spot spike is now emitted only where `top_time_ms < contact_time_ms`
(updip of the contact).

The 2D `inject_dhi_anomaly` has no horizon/relief concept (constant
`top_time_ms`), so it now takes `contact_time_ms` directly from the caller
and raises if `flat_spot=True` without one.

One notebook cell needed a manual update: `synthetic_dhi_generation.ipynb`
(cell id `841bf05c`) loops the 2D function over `SEVERITY_TIERS`, and
`tier4_obvious` has `flat_spot=True` — now passes an illustrative
`contact_time_ms` for that demo comparison.

**Verified:** reproduced the review's own check independently.

- Flat-spot event time across 3 simulated dip positions (top times 874/880/886ms,
  isolated by differencing wedge-with-flat-spot vs wedge-without): **900 → 902 → 900**
  (vs. the original bug's 904 → 908 → 916, which tracked the horizon 1:1).
- Downdip of the contact (top_time_ms=950 > contact=900): flat-spot
  contribution is exactly **0.0** — confirmed no event where there's no gas.

## F2 — Polarity reversal nulls the centre *(done)*

**Changed:** `injection.py` — `inject_dhi_anomaly_3d` and `inject_dhi_anomaly`.

3D: `polarity_reversal` now blends RC from `reflection_coefficient` (gas leg)
to `RC_WATER_SAND * water_leg_scale` (brine leg - real, weaker, opposite-signed,
never zero) across the same `contact_time_ms` introduced for F1, using a smooth
tanh transition rather than a hard linear ramp. The transition is keyed off
structural depth (`top_time_ms - contact_time_ms`), not lateral position in
the footprint, so it's anchored to the real fluid contact rather than the
footprint's geometric centre. `flat_spot` and `polarity_reversal` now share
one relief-derivation pre-pass (either flag triggers it), since a polarity
reversal and a flat spot are the same physical contact.

Blend width (`polarity_blend_ms`) is derived from the footprint's own average
dip rate (relief / footprint diameter) rather than a fixed constant, so it
scales with how steeply each specific footprint dips - "~2-3 traces" per the
review, translated into time via that footprint's own geometry.

2D `inject_dhi_anomaly` has no real horizon/depth, so the same non-zero-leg +
smooth-blend fix is anchored to lateral position (footprint centre) instead -
new `polarity_blend_frac` param (default 0.03) sets the transition width as a
fraction of the footprint's trace count.

**Verified:**

- Isolated the rc-blend formula directly (independent of wavelet convolution,
  which was muddying a first attempt at reading sign off the injected trace):
  stable at `-0.1545` (full gas RC) for `delta_t <= -6ms`, stable at `+0.0992`
  (full brine RC) for `delta_t >= +6ms`, smooth transition through `-0.0276` at
  `delta_t=0` (the contact itself) - **never zero**, unlike the original bug's
  exact `0.0` at the footprint's geometric centre.
- Real 3D injection (tier-4-like params, mock dipping horizon, contact landing
  exactly at the footprint's geometric centre by construction): centre-trace
  peak amplitude is `0.0397` (nonzero) vs. `0.0` in the original bug.

## F3 — Sag applied too deep, wrong order *(done)*

**Changed:** `injection.py::inject_dhi_anomaly_3d`, the sag block, two parts:

1. Onset moved from `wedge_t[-1]` (which carried `_fine_wedge`'s hardcoded
   `pad_ms=150`, and since F1 potentially the contact's extension too) to the
   actual reservoir base: `top_time_ms + twt_thickness_ms`.
2. **Reordered** so the sag is applied to the clean background (`volume`,
   untouched) first, and the wedge is added on top afterward - previously the
   wedge was injected first and the sag then interpolated from `out[i,j,:]`
   (already containing it), re-shifting/distorting part of the wedge itself.

**Verified:**

- Reservoir base for the review's own example (top=900ms, 14m reservoir,
  2000m/s) computes to **914ms**, and the sag's effect now starts at the very
  next sample (916ms at 2ms sampling) - no 148ms unshifted gap beneath the gas.
- Isolated the wedge's own contribution with a zero background: max mismatch
  between the injected wedge and its analytically-correct, un-shifted ground
  truth is **0.000000** - confirms the wedge itself is no longer being
  re-shifted by the sag now that the background-then-wedge order is enforced.

## F7 — Dataset export carried only 3 channels *(done)*

**Changed:** `attributes.py::compute_attribute_stack` extended from 3 channels
(amplitude, envelope, instantaneous phase) to 8: `amplitude`, `envelope`,
`inst_phase`, `inst_freq`, `sweetness`, `band_ratio`, `rms`, `local_var` -
the curated set from the runbook (C3), not all ~20 facies-pipeline attributes.
`band_ratio` (a bounded [-1,1] low-vs-high-frequency-band spectral contrast)
is new; the rest are standard reimplementations. Now takes `dt_s` (needed for
the frequency-based channels) and returns `(stack, channel_names)` instead of
a bare array, so channels stay traceable downstream.

`dataset.py::generate_example` updated to pass `dt_s=dt_ms/1000.0` and unpack
the new return; the `.npz` export now also saves `channel_names` alongside
`attribute_stack`/`mask`.

**Why this specific set, not all ~20:** bounded/relative channels transfer
across surveys, absolute-scale ones don't - not a theoretical concern here,
it's exactly what the regional-bias investigation on the `irp-nfs25` side of
this project found directly (raw_amplitude/apparent_polarity/relative_
acoustic_impedance flipped sign between train/test inline ranges, and
XGBoost trained on them collapsed to ~0 recall out-of-region). `band_ratio`
is bounded by construction; the others still carry the survey's absolute
gain, left to C4's window/whole-patch ratio feature construction to
neutralise rather than baking normalisation into the channels themselves.

**Verified:** stack shape `(8, n_il, n_xl, n_samples)` for a 3D patch, no
NaN/inf, `band_ratio` empirically within `[-0.99, 1.00]`. Full
`generate_example` → `.npz` save/load round-trip checked - `channel_names`
survives intact, shapes match. Checked for other callers of
`compute_attribute_stack` in the repo - only `dataset.py` uses it, already
updated.

**⚠️ Breaking change to flag on the `irp-nfs25` side (I can't edit that repo
directly, so noting it here):** `dhi_attribute_computation.ipynb`'s
`load_patch` step does `raw_amplitude, envelope, inst_phase = attribute_stack`,
which assumed exactly 3 channels in that fixed order. That unpacking will
raise `ValueError: too many values to unpack` once patches are regenerated
with this fix - needs a small update there (e.g. index by the new
`channel_names` array instead of positional unpacking). Also: the existing
184/184 patches in `F3_synthetic_dhi_dataset` were generated before this fix
and only have the old 3-channel stack - they'll need regenerating (rerun
`build_dataset`) to get the new channels at all.

My footprints are the large ones (1.5-4.0km vs. 0.28-0.40km on the other

## F5 — Background velocity for TWT: proposal

Wasn't a deliberate physical-modelling choice, but it's self-consistent -
the same velocity is used throughout the tier calibration, so the tier
ladder itself is unaffected by it. Proposing the model stays as-is, and the
quoted tuning-thickness number gets caveated as "background-velocity
apparent tuning thickness" rather than the true gas-reservoir value,
wherever either side quotes it in a write-up.

## C5 — Blind-exchange protocol: proposal

Accept the protocol as specified in the runbook as-is: report format (il/xl/
time origin, patch dimensions, `is_dhi`, predicted tier, a confidence score,
localisation mask with axes stated); hit = the detection's footprint
contains the true anomaly's map-view centroid, with IoU reported separately
as localisation quality rather than as the hit criterion; one detection
credited per anomaly (best overlap, duplicates reported but not
double-credited); hard-negative hits and F3's own real shallow-gas anomalies
each get their own category, neither counted as a false positive; each
detector frozen before it sees the other side's volume.

## C4 — XGBoost feature construction *(first iteration complete, `irp-nfs25` side)*

Lives in `dhi_detector.ipynb` (`irp-nfs25`), not this repo, so no diff to show
here - this is a status summary for visibility, not a fixes record.

**What's been built:** a second feature-construction approach alongside the
existing 42-attribute (whole-patch mean/max) pipeline, following the runbook's
C4: statistics computed in a small set of channels from the 8-channel
`attribute_stack` (`envelope`, `sweetness`, `inst_freq`, `band_ratio`),
expressed as a ratio of a windowed statistic to the same statistic over the
whole patch - intended to cancel the survey-level gain that made the
42-attribute pipeline's absolute-scale features fail to generalise out of
region. Also: `GroupKFold` by site (not a plain random split) for
cross-validation within train, the runbook's recommended regularised
hyperparameters, and reporting recall/F1 + recall-by-tier + hard-negative
false-positive rate by kind instead of accuracy.

**Iteration 1 (single ±60ms horizon-centred window, 12 features):** held-out
test recall **0.444** (vs. 0.067 on the 42-attribute pipeline, same
physics-fixed regenerated data) - a real improvement. `band_ratio` (the one
channel bounded by construction) took 3 of the top 6 feature-importance
slots, consistent with the bounded-channels-transfer hypothesis.

**Issue found:** recall by tier came back inverted (tier1_subtle 0.700 >
tier4_obvious 0.273 - "obvious" should be easiest, not hardest). Root cause,
confirmed empirically: tier4 uses `flat_spot`/`polarity_reversal` ~70% of the
time, and that signature sits at `contact_time_ms` (crest + half the
footprint's structural relief - see F1/F2 above), not at the horizon top the
single window is centred on. Checked all 17 real tier4 `flat_spot` examples
in the regenerated dataset directly: **12 of 17 (71%) have their contact
sitting outside the ±60ms window**, with observed relief up to 356ms on the
largest footprints.

**Note on attribution:** the runbook's C4 specifies exactly *one* ±60ms
window (the 12-feature version below, "iteration 1") - the two-window
near_top/below split that follows is not part of that spec. It's our own
fix, built in direct response to the tier-inversion issue found above. What
we did keep from the runbook is the governance rule around it - "add more
features only if grouped CV improves" - which the results table below checks
explicitly (0.381→0.524) before keeping the change. Flagging this
distinction since it's a real gap in the original C4 recipe itself (a single
horizon-top window structurally can't see a signal that sits deeper), not
just an implementation detail on our side - worth knowing for the other
pipeline too.

**Fix:** added a second, fixed "below" window (covering the region below the
reservoir out to the patch edge, generic and identical for every example)
alongside the existing "near_top" window, so a deeper contact-driven signal
is captured wherever it falls - deliberately *not* using the actual
`contact_time_ms` value to place the window, since that's ground-truth
information about the synthetic anomaly a real detector wouldn't have at
inference time (same leakage concern as "the footprint mask is a label, not
an input" in the runbook). First implementation had a real bug - the inner
per-statistic loop was indented outside the per-window loop, so only the
`below` window's values were actually being used (silently, under the old
single-window feature names) rather than both windows combining - caught via
the feature count staying at 12 instead of the expected 24. Corrected.

**Iteration 2 (near_top + below, 24 features) - results:**

| | Iter 1 (12 feat) | Iter 2 (24 feat) |
|---|---|---|
| grouped-CV recall | 0.381 | **0.524** |
| test recall / F1 | 0.444 / 0.500 | 0.467 / 0.512 |
| recall: tier1 / tier2 / tier3 / tier4 | 0.700 / 0.500 / 0.333 / 0.273 | 0.600 / 0.500 / 0.250 / **0.545** |
| FP: no_conformance / single_reflector / syncline / tuning | 0.368 / 0.300 / 0.000 / 0.357 | 0.421 / 0.200 / 0.000 / 0.429 |

The fix worked as diagnosed - tier4 recall roughly doubled - and grouped-CV
recall improved (0.381→0.524), which is the runbook's own stated bar for
justifying more features. Not a clean win across every slice, though: tier1/
tier3 recall and the no_conformance/tuning false-positive rates all got
somewhat worse, consistent with the classic small-n cost of doubling the
feature count (12→24) on the same ~95 training rows - the same tension
already seen once in this project at a larger scale (the 42-feature
collapse). `hard_negative_syncline` FP stayed at exactly 0.000 across every
iteration, a nice consistency check throughout.

**Current recommendation: stop feature-engineering iteration here.** Per the
runbook's own sample-size ceiling ("revisit only if the training set grows by
an order of magnitude"), the tier-curve non-monotonicity remaining (tier3 at
0.250) is more likely small-sample noise (~11-12 positives per tier in test)
than a further diagnosable mechanism - there's no equivalent concrete,
checkable cause the way the tier4/window-placement issue had one.
