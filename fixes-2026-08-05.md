## F4 — Footprint shrink: implemented

**Changed:** `FOOTPRINT_RADIUS_RANGE` (30, 80) -> (10, 15) traces in `scenarios.py`,
`il_extent`/`xl_extent` 160 -> 96 across `dataset.py`/`segy_export.py`/`real_examples.py`.
Also added the guard from your review's F4 action item: `generate_example` now skips
(rather than silently clips) any scenario whose footprint radius doesn't clear half the
patch extent, tracked as a new `footprint_exceeds_patch` skip reason.

**Number chosen — flagging for you to confirm:** I took your next-steps relief table
directly (footprint width ~20-30 traces post-F4) and halved it to a radius, since
`FOOTPRINT_RADIUS_RANGE` samples radius, not width -> (10, 15). This doesn't perfectly

F3's 25m trace spacing is closer to an 11-16 trace diameter, i.e. radius ~5.5-8) - close,
not identical. Worth pinning down the exact number together before any real C5 exchange,
since a mismatched footprint scale would confound the cross-test the same way the
original 5-10x gap would have.

`il_extent`/`xl_extent=96` matches what you'd already independently used - see
`real_dhi_extraction.ipynb`.

## New bug found: F4 exposed a gap in F1's own guard

**Where:** `dataset.py::generate_example`, calling `inject_dhi_anomaly_3d`.

F1's relief check (raise if a footprint's structural relief can't resolve a contact) is
correct on its own, but nothing caught it per-scenario - one bad random draw crashed the
entire `build_dataset` run instead of skipping just that one example. Smaller footprints
(F4) make this much more likely: relief scales with footprint size, so shrinking the
footprint shrinks the safety margin against the resolvability threshold too.

**Changed:** `generate_example` now catches this specific `ValueError` (and the analogous
F6 horizon-lookup-gap case) and returns a skip reason instead of raising -
`unresolvable_relief` / `horizon_lookup_gap`, same pattern as the existing F9
`il_xl_bounds`/`time_bounds` skips. Any other `ValueError` (e.g. a genuine kwargs
construction bug) still raises.

**Verified:** a synthetic zero-relief case correctly skips with `unresolvable_relief` and
no crash; a normal dipping-horizon case still succeeds unchanged (fix doesn't over-catch).

## Two-window re-measurement (next-steps §5.4): below window no longer earns its keep

This is the check your next-steps doc called for: "after F4 lands, re-measure with and
without the second window... if most of the benefit has evaporated, reverting to the
12-feature version is worth considering." Reran both configs (`irp-nfs25`'s
`dhi_detector.ipynb`) on the new 520-example dataset:

| | 12-feat (near_top only) | 24-feat (near_top + below) |
|---|---|---|
| grouped-CV recall | 0.150 | 0.150 |
| test recall / F1 | 0.400 / 0.497 | 0.410 / 0.497 |
| recall: tier1 / tier2 / tier3 / tier4 | 0.259 / 0.519 / 0.448 / 0.364 | 0.222 / 0.481 / 0.448 / 0.500 |
| FP: no_conformance / single_reflector / syncline / tuning | 0.000 / 0.382 / 0.000 / 0.360 | 0.024 / 0.412 / 0.000 / 0.400 |

**Grouped-CV recall is identical - not just the mean, every individual fold matches**
(0.000 / 0.000 / 0.600 / 0.000, both configs). With 12 more features available and zero
change to a single held-out prediction across any fold, the regularised model isn't using
the `below` window's features at all under cross-validation - they're inert there.

The test-set differences (tier4 recall 0.364 -> 0.500, test recall 0.400 -> 0.410) are
real but small (one flipped prediction out of 105 test positives), and consistent with the
`below` features aligning with this *particular* fixed test split's sites rather than
generalising - exactly the failure mode grouped-CV (resampling which sites are held out)
is designed to catch, and did catch here.

Combined with `no_conformance`/`tuning` FP rates both getting worse for zero verified CV
gain, this matches what F4 was supposed to do: shrinking the footprints brought the
contact back inside the primary `near_top` window for most examples, so the `below`
window's original job (catching a contact that fell outside it) is now mostly redundant.

**Recommendation: revert to 12 features (near_top only).** Simpler model, same verified
CV performance, better hard-negative FP rates.
